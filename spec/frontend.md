# Front-End Specification (Kustavi GUI)

## 1. Overview

The Kustavi GUI is a C++ desktop application, built with the Basalt widget
library and the Magma windowing and rendering library, that drives a wizard
over a folder of images. The first stages are linear; the review stage is a la carte:

1. Select folder (with visual confirmation grid and automatic session recovery)
2. Organize — trips pass: spatiotemporal grouping with user thresholds and
   per-photo curation. Its folders become the **batches** reviewed next.
3. Review — a batch menu. For each batch the user runs whichever passes they
   want, in any order: quality (blurry / poorly exposed), duplicates
   (similar-image groups, keep-one selection), junk (screenshots and
   non-photographs, local vision LLM) and video. Each pass opens its own
   review and returns to the menu. Passes skip photos already marked for
   deletion where that saves work.
4. Copy — copy the kept images to a user-chosen destination

All user input is handled here. All image processing lives in the C++
back end, which the GUI launches, supervises, and talks to over gRPC on a
loopback TCP port. The normative API is defined in `spec/proto.md`.
Back-end behavior is specified in `spec/backend.md`.

State is persistent per folder: the back end maintains an embedded SQLite database 
file (`.kustavi-cache/session.db`) inside a hidden cache folder within the target 
source folder root. If a user exits mid-wizard, re-opening that same folder 
restores their exact phase progress, pre-calculated image metrics, and explicit deletion flags.

## 2. Platforms & Build

- Targets: macOS, Windows, Linux desktops. macOS is the platform that the code
  has been run on so far.
- Built with CMake, as part of the repository's single build (`CMakeLists.txt`).
  `KUSTAVI_BUILD_GUI=ON` adds the GUI, whose Basalt and Magma sources come from
  checkouts (`KUSTAVI_BASALT_SOURCE_DIR`, `KUSTAVI_MAGMA_SOURCE_DIR`) until
  releases of both are pinned in `cmake/dependency_pins.cmake`. `just build-gui`
  builds it, `just run-gui` runs it from the build tree, and `just package`
  builds the redistributable (`tools/package.py`).
- Rendering uses the graphics API that `magma::preferred_graphics_api` picks:
  Metal on macOS, Vulkan on Linux, Direct3D 12 on Windows. The raster backend is
  the fallback on a machine without a usable GPU and renders the images in
  tests.
- Video playback uses libmdk, a pinned release archive that the build fetches
  (`KUSTAVI_ENABLE_VIDEO`, `KUSTAVI_MDK_DIR`). A build without it shows the
  still image of a video.
- The code follows `spec/CONVENTIONS/C++.md`. The warning set of the build is
  strict, and a change must compile without warnings.
- Window: default 1280×800. English-only UI.

## 3. Process Model

### 3.1 Launching the back end

The GUI is the supervising process. On app start it launches exactly one
back-end process.

Binary discovery, in order:

1. `KUSTAVI_BACKEND_PATH` environment variable (absolute path) — used in
   development to point at the CMake output (`.build/debug/backend/server`).
2. `kustavi-backend` (or `kustavi-backend.exe`) in the same directory as
   the running GUI executable. On macOS this is
   `<App>.app/Contents/MacOS/kustavi-backend`.

If the binary is not found, the GUI shows a start-up error screen
("Back end not found. Set KUSTAVI_BACKEND_PATH or install the back end
next to the app.") with a single [Exit] button. The wizard cannot start
without the back end.

Launch arguments: `--listen 127.0.0.1:0 --token <auth_token> --log-file <log_file> --parent-pid <gui_pid>`
(port 0 = OS-assigned; `<auth_token>` is a secure random string generated by the GUI on startup to authenticate gRPC requests; `<log_file>` is a unique per-launch file inside the OS temp directory, e.g. `kustavi-backend-20260824-143012-a1b2c3d4.log` in `/tmp` — the back end appends all log output to it while continuing to mirror it on stderr; `<gui_pid>` is the GUI process id, used by the back end's parent watchdog in §3.2).

Ready handshake:

1. After binding its socket, the back end prints exactly one line to
   stdout, flushed immediately: `KUSTAVI-READY <port>\n`.
2. The GUI waits up to 30 s for that line, opens a gRPC channel to
   `127.0.0.1:<port>`, and calls `GetInfo` (5 s deadline) as a readiness
   probe. The random auth token must be embedded in the gRPC metadata header 
   for this and all subsequent communications.
3. If the line does not arrive, is malformed, or `GetInfo` fails: start-up
   error screen with [Retry] (relaunch) and [Exit].

All other back-end stdout/stderr lines are captured into an in-memory
ring buffer (256 KB) and shown in a "Back end log" dialog reachable from
the app menu.

### 3.2 Supervision

- The GUI watches the back-end process for exit.
- Unexpected exit while the app is alive triggers the crash dialog (§10.1).
- Clean shutdown (app quit or after the Done screen): GUI calls
  `Shutdown`, waits up to 3 s for process exit, then kills the process if
  it is still alive. The GUI also runs this clean shutdown when the OS
  requests app termination (window close, Cmd/Ctrl+Q) via
  `WidgetsBindingObserver.didRequestAppExit`.
- Backstop against orphans: the back end is launched with `--parent-pid
  <gui_pid>` and runs a background watchdog that force-exits
  (`std::_Exit`) as soon as the GUI process is gone — covering exits that
  never reach the clean-shutdown path (GUI crash, `SIGKILL`, a debugger session
  that is stopped). The watchdog polls every 500 ms.
- The GUI never runs more than one back-end at a time. "Retry" after a
  crash starts a fresh process and repeats the ready handshake.

### 3.3 Transport

- gRPC over HTTP/2, insecure credentials with loopback TCP only + GUI generated Auth Token validation.
- The channel and the child process are owned by `backend_host`
  (`gui/core/backend_host.h`). It starts the back end off the UI thread, reports
  when it is ready, has died or could not start, restarts it, and stops it at
  exit. The auth token goes in the metadata of every call.

## 4. API Integration

The GUI consumes `spec/proto.md` through a single wrapper interface so
screens and the wizard controller never touch generated stubs directly
(`gui/core/kustavi_client.h`):

```cpp
class kustavi_client {
public:
  virtual auto get_info() -> call_result<GetInfoResponse> = 0;
  virtual auto shutdown() -> call_result<void> = 0;
  virtual auto inspect_session(std::string folder) -> call_result<InspectSessionResponse> = 0;
  virtual auto get_session_results() -> call_result<GetSessionResultsResponse> = 0;
  virtual auto save_session_state(SaveSessionStateRequest) -> call_result<void> = 0;
  virtual auto preview_quality_thresholds(PreviewQualityThresholdsRequest) -> ... = 0;
  virtual auto estimate_commit(CommitRequest) -> call_result<EstimateCommitResponse> = 0;

  virtual auto scan_folder(ScanFolderRequest, stream_handlers<ScanEvent>) -> stream_subscription = 0;
  virtual auto run_quality_pass(...) / run_junk_pass(...) / run_similar_pass(...)
      / run_video_pass(...) / run_trips_pass(...) / ensure_model(...) / commit(...);
};
```

- A unary call returns `std::expected<T, backend_error>` and blocks, so the
  controller runs it on a worker. A streaming call starts its own worker, which
  reads the stream and calls the handlers, and the handlers only post to the UI
  queue (§9). Destroying or cancelling the `stream_subscription` cancels the
  call, which stops the back-end pass (proto spec §2); after a cancel no handler
  runs again.
- The production implementation is `grpc_kustavi_client`. It maps status codes
  to `backend_error` (§10.5).
- A `fake_kustavi_client` (`gui/testing/`) plays back scripted events and
  records the requests, for tests.
- At most one analytical pass RPC is in flight at a time. The GUI must not start a
  new pass stream until the previous one has completed. `EnsureModel` is an explicit exemption to this rule, allowing it to run concurrently as a background process during folder scanning or quality review.

## 5. Domain Model (C++)

Plain value types in `gui/core/domain.h`, built from proto events:

- `image_info`: id, path, name, size, width, height, `optional<time_ms> taken`,
  `optional<geo_point> gps`, `working_image_path`, `is_video`, video duration.
- `quality_flag_info`: image id, reasons (`blurry`, `under_exposed`,
  `over_exposed`), sharpness, exposure score.
- `junk_flag_info`: image id, reason text, confidence. `video_flag_info`: the
  same for a video, with a reason such as `too_short`.
- `similar_group_info`: id, member ids, recommended keep id, per-member scores.
- `trip_info`: id, start/end time, member ids, centroid, folder name, folder
  slug, place name, `vector<trip_leg_info>` legs, `is_home` flag.
- `trip_leg_info`: place name, slug, member ids, centroid — one contiguous stay
  within a trip.
- `deletion_intent` (`gui/core/deletion.h`): `explicit_kept`, `explicit_deleted`
  and the keeper that the user chose for each duplicate group, to preserve user
  intent across automated pass defaults.
- `wizard_phase`: a `std::variant` of the phases (§6), in `gui/core/phases.h`.

Errors are values: `backend_error` is a `std::variant` of `backend_crashed`,
`backend_rpc` (status code and message), `backend_startup_failed` and
`backend_not_found`. Operational failures are returned and not thrown.

The image index (`unordered_map<string, image_info>` plus the ids in scan
order) is built incrementally from `ScanFolder` events and kept in the wizard
controller. It is the single source of truth for image metadata in the GUI.

## 6. The Wizard

### 6.1 Step indicator

A top bar shows four stages — Select, Organize, Review, Copy — with the
current stage highlighted and completed stages checked. The indicator is
display-only; navigation is via the bottom action bar. Passes do not appear
in it, because they run in any order inside the Review stage.

### 6.2 Steps

**S0 — Start.**
UI: app title, [Select folder…] button. If the vision model is still
preparing in the background (§6.3), a small card shows
"Preparing vision model — 42% (1.2 / 2.9 GB)".
Action: directory picker (`file_picker`); on selection, call
`ScanFolder`. 

**S0-B — Session Restore Prompt (Conditional).**
UI: Triggered if `ScanFolder` finishes with `resumed_session == true`. Displays a card: "Saved Session Detected. Found <N> localized assets with partial processing history." 
Buttons: `[Resume Saved Session]` (hydrates results and choices, re-runs the trips pass, and lands on S4 or S11; see Resume under §6.4), and `[Start Fresh]` (re-runs `ScanFolder` with `force_fresh = true` to wipe the DB and cache).

**S1 — Scanning.**
UI: indeterminate-ish progress: images found so far, current path being
scanned, [Cancel].
Exit: `ScanComplete` (with no resume history found) → S2. Zero images found → "No images found in
<folder>" screen with [Choose another folder] (→ S0) and [Exit].
Cancel → S0.

**S2 — Confirm folder.**
UI: header "<N> images in <folder>"; grid of every image (768px working previews +
file names); [Back] (→ S0, discards scan results if a fresh session) and [Continue] (→ S3).
Clicking an image opens the detail view (§7.2) in read-only mode
(metadata only, no deletion toggle).

**S3 — Organize (trips).**
Entry: [Continue] from S2 runs `RunTripsPass` with the current slider values
(defaults: gap 48 h, drift 300 km, away-from-home 15 km, new-leg 25 km). It
runs first because it is cheap, needs only metadata, and defines the batches.
UI: progress while running ([Back] cancels to S2), then the trips review:
- **Clustering settings** (collapsible): four sliders — "Max time gap"
  (1–168 h), "Max trip drift" (10–1000 km), "Away-from-home distance"
  (1–100 km), "New-leg distance" (1–200 km) — a "Re-cluster" button, and
  an "Organize output into trip folders" switch (default on). Re-cluster
  re-runs the pass and **discards manual trip edits** (a message at the bottom of
  the window says so), since edits are defined against the previous clustering.
- **Folders** group trips by their display name ("Rome, Italy · April
  2026", or "April 2026" without geo). Folder headers are inline-editable
  (renames every trip in the folder). At-home photos appear in
  "Home · <month>" folders.
- **Trips** show the place label, date range, photo count, and — for a
  multi-leg trip — one labelled sub-grid per leg. `isHome` trips carry a
  home icon.
- **Per-photo curation.** Each trip has a select toggle: in select mode,
  tapping photos picks them and a "Move to trip ▸" menu reassigns the
  selection to another trip, a **new trip**, or **removes** it from every
  trip. A hand-made trip inherits its place name from the source photos'
  original cluster when they were geocoded. Outside select mode, tapping a
  photo opens the detail view (the deletion toggle is enabled). An
  **"Unassigned"** section at the bottom lists photos in no trip with an
  "Add to trip ▸" menu.
- Reassignments are client-side overlays on the clustering result; they
  feed `CommitRequest.folder_for_id` at commit when the organize switch
  is on.
[Back] (→ S2), [Continue] (→ S4). Continue fixes the batches: one per output
folder, plus an "Unassigned" batch for photos in no trip. Membership is
frozen at that point.

**S4 — Batch menu.**
UI: header "<B> batches · <M> of <N> photos marked for deletion". A list of
batches (name, photo and video counts, number of passes done) sits beside the
selected batch's pass cards, in the suggested order Quality, Duplicates, Junk,
Video (Video only when the batch has videos). Each card names the pass, its
cost ("fast", "slow, about 2 s per photo"), and its status: "Not run", "Done ·
<n> flagged" (groups for duplicates). Buttons: [Run] / [Review] + [Run again],
and [Run on all batches], which runs the pass on every batch that has not
finished it, one after another, then returns here.
The suggested order puts the cheap passes first so the slow junk pass skips
photos they already marked, but nothing enforces it.
[Edit trips] (→ S3 trips review; batch progress marks are dropped because the
batches are rebuilt), [Continue] (→ S10).

**S5 — Pass running (per batch).**
Entry: [Run] on a pass card. The pass runs with `scope_image_ids` set to the
batch and `batch_key` set to the batch key, so it analyzes only that batch and
records a per-batch completion. Junk and duplicates are also sent
`skip_image_ids` (photos already marked for deletion); video sends the same.
UI: progress, [Cancel] (→ S4). If the vision model is not ready when junk is
chosen, a "Downloading vision model" screen shows byte progress, speed and
[Cancel] (→ S4); download failure shows an error screen with [Retry download]
and [Exit app] (no skip option: the junk pass always uses the LLM). When the
model is ready the junk pass starts automatically. The junk pass copy makes the
~1.5–3 s per image cost explicit.

**S6 — Pass review (per batch).**
Each pass has its own review, limited to the active batch:
- **Quality.** Header "<X> of <N> images flagged" for the batch. A keep
  section and a collapsible delete panel, reason chips ("Blurry",
  "Overexposed"); tapping a cell moves it between them. Threshold sliders
  (collapsed by default) carry direction hints ("fewer flagged" / "more
  flagged"; the blur and exposure sliders run in opposite directions) and a
  line under them shows how many images the current slider values would flag
  in this batch (`PreviewQualityThresholds` with the batch scope), next to the
  count from the last run. [Rerun pass] re-runs the batch with the new values.
  A flagged photo with unflagged photos taken within two minutes of it (up to
  two on each side, videos excluded) shows an "N nearby" chip. The detail view
  lists those photos as thumbnails under "Nearby shots"; tapping one opens it.
- **Junk, Video.** Same keep / delete layout, most confident first; reason
  chips show the classification.
- **Duplicates.** Group cards: "Group <i> — <M> similar photos", a row of
  member cells with the suggested keeper pre-selected, [Keep all] and
  [Delete all] per group.
Buttons: [Keep all] / [Mark all] (flagged photos in this batch), [Done] (→ S4).
Cell click opens the detail view with the deletion toggle enabled. Marks
update live inside `DeletionPlan`.

**S10 — Final review.**
Entry: [Continue] on the batch menu. Header: "<N> photos marked for deletion".
Every photo marked by any pass or by the user is listed, grouped by batch in
batch order, with one reason chip per cause (quality reasons, junk category,
video reason, "Duplicate", "Marked by you"). Batches with nothing marked are
left out. Tapping a photo keeps it and removes it from the list. [Back]
(→ S4), [Continue] (→ S11).

**S11 — Commit summary.**
UI: "Keep <N> photos (<total size>) — <M> will be left behind".
Destination: text field + [Choose folder…] (directory picker; the
suggested default, pre-filled, is a sibling of the source named
`<source-name>-kept`). [Back] (→ S10). [Copy] (disabled until a
destination is set and space availability is confirmed) → S12.
The screen calls `EstimateCommit` (with `merge_existing`) when it opens and,
debounced, when the destination changes, and shows "Needs <size> · <free>
free · <n> already there". When the estimate says the copy does not fit, the
line turns to an error and [Copy] stays disabled. S13 reports how many
photos were already in the destination.

**S12 — Committing.**
Entry: `Commit` with `destination` and calculated user/automated `keep_ids`.
UI: progress "<done> / <total> files (<done_bytes> / <total_bytes>)", current file name, [Cancel] (→ S11;
partially copied files remain — re-committing is safe, see proto spec).
Exit: `CommitComplete` → S13.

**S13 — Done.**
UI: "Copied <n> photos to <destination>". If there were skips or errors,
they are listed. Note: "Your original files were not modified. You can
safely delete the source folder."
Buttons: [Start over] (resets the wizard to S0 in the same app session,
starting a new back-end session) and [Done] (shuts down the back end and
quits the app).

### 6.3 Vision model preparation

- On app start (S0), the GUI begins `EnsureModel` as a background
  call, followed by `model_status`. Model states: `unknown → downloading(progress) → ready` or
  `failed(message)`.
- `ready` is cached for the session. Moondream-3.1 INT4 weights take ~1.1 GB memory.
- S5 waits for the same `model_status` and renders its state.
- The model name/size come from the `GetInfo`/`ModelReady` events.

### 6.4 Transition table

| From | Trigger | To |
|---|---|---|
| S0 | folder selected | S1 |
| S1 | scan complete, resumed_session == true | S0-B (Prompt Card) |
| S1 | scan complete, resumed_session == false, images > 0 | S2 |
| S1 | scan complete, 0 images | no-images screen → S0 |
| S1 | cancel | S0 |
| S0-B | Resume Saved Session | S4 (or S11 if saved there), after the trips pass re-runs |
| S0-B | Start Fresh | S1 (with wipe directive) |
| S2 | Back | S0 |
| S2 | Continue | S3 (trips pass runs) |
| S3 | trips complete | S3 trips review |
| S3 | cancel while running | S2 |
| S3 | RPC error | error screen (§10.2) → S2 or exit |
| S3 | Back (trips review) | S2 |
| S3 | Continue (trips review) | S4 (batches built) |
| S4 | Run / Run again on a pass card | S5 (junk: model prep first if the model is not ready) |
| S4 | Run on all batches | S5 for each unfinished batch in turn, then S4 |
| S4 | Review on a finished pass | S6 |
| S4 | Edit trips | S3 trips review |
| S4 | Continue | S10 |
| S10 | Continue | S11 |
| S10 | Back | S4 |
| S5 | complete (single batch) | S6 |
| S5 | cancel | S4 |
| S5 | model ready (junk) | pass starts |
| S5 | download failed | error screen → retry or exit |
| S5 | RPC error | error screen → S4 |
| S6 | Done | S4 |
| S11 | Copy | S12 |
| S11 | Back | S10 |
| S12 | complete | S13 |
| S12 | cancel | S11 |
| S13 | Start over | S0 (fresh session) |
| S13 | Done | app quit |

Back navigation never re-runs a completed pass; it revisits the previous
screen with its stored results. A cancelled pass leaves the batch's earlier
results as they were, and the user can run it again from S4.

**Resume.** Resuming a saved session restores the index, every pass result
and the user's decisions, then re-runs the cheap trips pass (there is no
persisted trips result) and lands on S4 — or S11 when the session was saved on
the commit summary. A pass the saved session finished over the whole library
counts as done for every batch; per-batch completions come back in
`completed_batch_passes`. Manual trip edits (moved photos, hand-made trips,
renamed folders, the folder-layout switch) are saved with the session as an
opaque `trip_edits` string and laid back over the new clustering when the
trips pass finishes on resume. An edit is dropped when its photo no longer
exists, when it names a trip id the new clustering did not produce, or when a
renamed trip's generated name differs from the one recorded at the time. Re-running
the trips pass with new settings discards the edits, on disk as well.

## 7. Shared UI

### 7.1 Image grid

- Basalt's `grid_view`: virtualized, with a fixed 160 px cell, a gap, and
  sections with a header row. It creates widgets only for the rows in view and a
  margin, and reuses the cells that scroll away. `image_grid`
  (`gui/app/image_grid.h`) fills it from groups of photos and keeps the decoded
  images in a cache that the screens share.
- Cell: a Basalt `image_tile` with the cached 768px working image
  (`working_image_path`) and a one-line caption. A worker pool decodes the
  images of the cells in view first. Badges are small chips in the corners of the
  tile: step reason chips, "keeper", "suggested" and "delete".
- Badges reflect evaluating user hierarchy live.
- Cell click → the action of the screen: open the detail view, move the photo
  between the keep and delete lists, or make it the keeper. A button in the top
  right corner of a cell opens the detail view where a click means something
  else.

### 7.2 Detail view

An overlay dialog over the current screen (`gui/app/detail_view.h`):
- Progressive loading pattern: Instantly loads and displays the cached 768px `working_image_path` JPEG image. Concurrently decodes the full-resolution master asset (`image_info::path`) on a worker thread of its own loader. Once completed, it replaces the picture in the zoomable viewport (`zoom_view`, 1×–8×, wheel and buttons zoom, drag pans, double-click resets) without moving the view.
- The decoded master belongs to the loader's results and to the viewport only, so it is freed with the view when the dialog closes.
- A video plays through libmdk (`gui/app/video_player.h`). The player decodes on its own threads, converts each frame to RGBA at no more than 1600 px on the longer side, and keeps only the newest, which the UI thread copies into an image. A Play/Pause button controls it. Without libmdk, or if the file cannot be played, the still image stays.
- Metadata panel: name, path, dimensions, file size, date taken, GPS coordinates, sharpness/exposure scores, junk and video reasons, trip, leg and place, and the nearby shots of a flagged photo.
- "Marked for deletion" switch: enabled everywhere except the folder confirmation (S2), where it is read-only.
- Close: [Close] button or Esc key.

## 8. Deletion Model

`deletion_intent` is driven by two isolated user tracking configurations: `explicit_kept` and `explicit_deleted`. 

When evaluating whether an asset displays a deletion marker badge, the interface evaluates this deterministic order:
1. **Is the ID found in `explicitDeleted`?** → Display Red Deletion Tag badge.
2. **Is the ID found in `explicitKept`?** → Hide Deletion Tag badge.
3. **Step Default Automation Fallback:**
   - Quality pass (S6): Marked for deletion if flagged by back-end metrics.
   - Junk pass (S6): Marked for deletion if flagged by Moondream LLM inference.
   - Duplicates pass (S6): Marked for deletion if the asset is not the designated group keeper.

Final resolution parameter computation at S11/S12 happens downstream via the C++ SQLite aggregation layer. The GUI never passes delete instructions directly.

## 9. State Management

The UI thread owns every Basalt object and all application state. Worker
threads do blocking work and decoding, and hand their results back through
`ui_queue` (`gui/core/ui_queue.h`), whose `post` is safe on any thread and whose
`drain` runs the tasks on the UI thread. Posting wakes the event loop. Basalt's
`text_shaper` is not thread-safe, so only the UI thread builds or measures
widgets.

- `wizard_controller` (`gui/core/wizard_controller.h`) holds the current phase
  and the image index, the passes' flags, the user's choices, the trips plan,
  the batches and the commit state. It applies the results that arrive through
  the queue and the user's actions, and calls its change handler. The
  implementation is split by responsibility: the session and scan, the trips,
  the batches and passes with the deletion choices, and the commit.
- `ui_scope` drops the result of an operation that a newer one replaced, and a
  result for an object that no longer exists. A controller or a model status
  starts a new generation for each stream or call.
- `ui_timers` holds one-shot timers on the UI thread, such as the pause before
  an estimate request.
- `model_status` follows the `EnsureModel` background pipeline.
- `backend_host` owns the back-end process and its client (§3).
- Screens build their widget subtree from the controller's state and are built
  again when it changes (`wizard_shell`). A change that must not rebuild what
  the user is using, such as a slider being dragged or a destination being
  typed, updates the existing widgets in place.

## 10. Error Handling

### 10.1 Back-end crash

A modal dialog over whatever step is active: "Processing error: the
back end stopped unexpectedly."
- [Retry]: relaunch back-end process using a clean auth token hand-shake. Re-runs current volatile operational streams or picks up from saved state if table markers are present.
- [Exit app]: quit.

### 10.2 Step failure

A pass RPC that terminates in a non-cancel gRPC error: an error screen with the back-end message and
[Back] and [Exit app].

### 10.3 Model failure

Covered by S5 (§6.2): [Retry download] or [Exit app]. No skip.

### 10.4 App quit mid-session

Closing the window mid-session triggers process teardown after finalizing pending transactional statements.

### 10.5 Error mapping

gRPC status → `BackendError`: `NOT_FOUND` → `NotFound`; `UNAVAILABLE` during a call → treated as crash (10.1); anything else → `Rpc` message strings surfaced verbatim.

## 11. Performance & Memory (16 GB machine)

- High-resolution master assets are isolated to background threads and evicted instantly after use. The interface scales cleanly utilizing downscaled 768px images.
- Target: < 1 GB GUI RSS with a 50,000-image folder. 
- The backend manages memory by unloading the Moondream-3.1 engine model context from active allocation when navigating away from the Junk pass step.

## 12. Testing

Tests run under CTest with Catch2 (`just test-gui`; `just test-gui-core` runs the
tests that need no window library). Labels: `gui`, `process`, `grpc`. The sanitize
test preset leaves out `grpc`, because a gRPC server in the test mixes sanitized
and unsanitized code. They cover:
- Folder initialization workflows including scanning, resume prompts, and force-fresh wipe behaviors.
- Deletion model fallback hierarchy rules.
- Every phase transition of the controller, driven by `fake_kustavi_client`, with the posted results drained by hand.

## 15. Decisions Recorded

- Triage scope is explicitly restricted to standard raster extensions (`jpg`, `jpeg`, `png`, `heic`, `heif`, `webp`, `tiff`, `tif`, `bmp`, `gif`). RAW file workflows are excluded.
- The 256px thumbnail tier is eliminated; a unified 768px downscaled layer serves both UI visualization and Moondream LLM input encoding pipelines.
- Sidecar assets matching target paths (e.g. `.xmp`, `.aae`) are copied automatically by the C++ file execution loop during the `Commit` pass phase.
- Scanning is recursive (subfolders included) by default.
- The destination folder is always user-chosen; the pre-filled suggestion is a sibling directory named `<source-name>-kept`.
- Cancelling a running pass returns to the preceding step; the pass is
  re-run from scratch if the user continues forward again.
- The junk pass always uses the LLM; there is no OpenCV-only mode and no
  user-facing model configuration.
- The vision model download starts in the background on app start so it
  is usually finished by the time the junk pass is reached.
- Bulk decisions exist only as per-step actions ([Keep all]/[Mark
  all]/[Delete all]); there is no free-form multi-select — except on the
  trips step, where a per-trip select mode drives photo reassignment.
- The trips step is organizational: it shows home-anchored trips, lets the
  user re-cluster, rename folders, and move photos between trips, and (via
  the detail view) make per-image delete decisions. The effective trip
  layout drives the committed folder structure when "Organize output into
  trip folders" is on.
